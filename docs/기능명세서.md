## 0. 이 문서의 범위와 원칙

본 명세서는 **실제 구현된 코드를 기술한다.** 계획이나 의도가 아니라 저장소에 있는
동작을 적으며, 구현되지 않은 항목은 12장에 **알려진 제약**으로 명시한다.

### 서비스 원칙

> **숫자는 확정, 제도는 후보.**
>
> **확정 제시** — 총 채무액, 월 상환 부담, 월 가용재원, 월 부족액.
> 결정론적 계산 모듈이 산출하며 LLM이 개입하지 않는다.
>
> **후보 제시** — 채무조정 제도 적합성, 신청 가능 여부, 감면 범위.
> 판정하지 않고 충족·미확인 조건과 공식 근거를 함께 제시한다.

### 설계 불변 조건

| ID | 조건 | 구현 위치 |
|---|---|---|
| INV-1 | 추출된 모든 필드가 사용자 확인을 마치기 전에는 계산·판정을 실행하지 않는다 | `pipeline/stages.py:transition` → 409 |
| INV-2 | 화면의 모든 금액은 계산 모듈 산출값이다. LLM이 만든 숫자는 표시하지 않는다 | `narrative/grounding.py` 숫자 대조 → 실패 시 템플릿 대체 |
| INV-3 | 제도 조건 문장은 정책 카드 원문만 인용한다 | `rules/policy_card.py` + 화면 06 `policy_ref` |
| INV-4 | 출처가 검증되지 않은 제도 조건은 UNKNOWN으로 처리한다 | 카드 `verified` 플래그, `unresolved` 블록 |
| INV-5 | "모른다"를 "아니다"로 취급하지 않는다 | `ConditionState` 3-state, `condition_eval.py` |
| INV-6 | 계산 모듈은 현재 시각·난수·외부 IO를 참조하지 않는다 | `cashflow/calculator.py` 순수 함수, 기준일은 `as_of` 인자 |

## 1. 시스템 구성

### 1.1 기술 스택

| 계층 | 기술 |
|---|---|
| API | FastAPI (Python 3.11) |
| 화면 | Jinja2 서버 사이드 렌더링 + Tailwind CDN + htmx |
| 도메인 모델 | Pydantic v2 (`frozen=True`, `extra="forbid"`) |
| LLM | Anthropic API 우선 → 미설정 시 로컬 오픈모델(Qwen2.5-7B GGUF, `llama-cpp-python`) → 그마저 없으면 `StubClient` |
| 문서 처리 | pypdf · pdf2image |
| 요약서 | WeasyPrint |
| 세션 저장 | SQLite (`SqliteSessionStore`, `DN_SESSION_DB` 경로) — 프로세스 재시작에도 세션 유지 |

### 1.2 모듈 구성

```
src/dn/
├── main.py            앱 팩토리 · 전역 예외 핸들러 · TTL 스위퍼 lifespan
├── api/               라우터 3종 (session · document · analysis)
├── web/               화면 8종 + 라우터
├── ingest/            업로드 검증 · PDF 판독 · PII 마스킹 · 인젝션 스캔
├── extraction/        LLM 추출 · 정규화 · 스키마 검증
├── reconcile/         누락(Gap) · 모순(Conflict) 탐지 · 질문 선별
├── cashflow/          결정론적 계산 · 시나리오
├── rules/             정책 카드 · 3-state 조건 평가 · 규칙 엔진 · 트리아지
├── narrative/         설명 생성 · 숫자 그라운딩 검증 · 템플릿 폴백
├── safety/            입력·출력 필터 · 감사 로그 편집
├── report/            상담용 요약서 PDF
├── pipeline/          상태머신 · 오케스트레이터
├── storage/           세션 저장소 · TTL 스위퍼
└── domain/            모델 · 열거형 · 예외 · 출처 추적
```

### 1.3 처리 파이프라인

```
업로드 → 검증 → PDF 판독 → 인젝션 스캔(라인 제거) → PII 마스킹
   → LLM 추출 ─────────────────────────────── LLM 개입 지점 1
   → 사용자 확인 ────────────────────────── 인간 감독 지점 1 (INV-1 게이트)
   → 누락·모순 탐지 → 보완 질문 → 보완 입력
   → 현금흐름 계산 ───────────────────────── 확정 숫자 (항상 실행)
   → 트리아지 (REFER 시 규칙 엔진 생략)
   → 정책 카드 로드 → 3-state 조건 평가 → 경로 선별(최대 3)
   → 설명 생성 ─────────────────────────── LLM 개입 지점 2
   → 출력 필터 + 그라운딩 검증 → 실패 시 템플릿 대체
   → 7일 계획 → 상담용 요약서 PDF ──────── 인간 감독 지점 2 (공식 상담 연계)
```

**`cashflow` 는 항상 계산·반환된다.** 정책 카드를 못 불러오거나 규칙 엔진이 실패해도
`undetermined=True` 로 강등될 뿐 상환여력 결과는 그대로 제공한다(기획서 7.3).

### 2.1 상태

| 값 | 단계 | 비고 |
|---|---|---|
| `s0_consent` | 동의 | 세션 생성 직후 |
| `s1_uploaded` | 업로드 대기 | 동의 완료 |
| `s2_extracted` | 추출 완료 | |

| `s4_supplemented` | 보완 입력 완료 | |
| `s5_analyzed` | 분석 완료 | |
| `s6_planned` | 계획 생성 | |
| `s7_reported` | 요약서 생성 | **인간 감독 지점 2** |

### 2.2 전이 규칙 (`pipeline/stages.py`)

| 규칙 | 동작 |
|---|---|
| 자기 자신으로 전이 | 금지 |
| 다음 단계로 전진 | 허용 (**건너뛰기 불가**) |
| 이전 단계로 후진 | 허용 (임의 단계) |
| 2단계 이상 점프 | `StateTransitionError` → **409** |

**추가 규칙 두 가지**

1. **INV-1 게이트** — `S2 → S3` 전이는 `extraction.all_confirmed == True` 여야 한다.
   `creditor` `product_type` `balance` `overdue_days` `is_secured` 5개 필드가
   채무마다 `user_confirmed == True` 여야 성립한다.
2. **롤백 시 산출물 무효화** — `S5` 이상에서 후진하면 `analysis` 의
   `cashflow` `rules` `narrative` 를 `None` 으로 지운다. 오래된 산출물 재사용을 막는다.

모든 도메인 모델이 `frozen=True` 이므로 전이는 원본을 바꾸지 않고 새 객체를 반환한다.

## 3. API 명세

모든 라우터의 prefix 는 `/api/session` 이다. 응답 오류는 `{"detail": "<한국어 메시지>"}` 형태다.

### 3.1 세션

| 메서드 · 경로 | 요청 | 응답 | 전이 | 오류 |
|---|---|---|---|---|
| `POST /api/session` | — | `{session_id, stage}` **201** | → S0 | — |
| `POST /{id}/consent` | — | `{session_id, stage}` | S0 → S1 | 404 · 409 |
| `DELETE /{id}` | — | **204** | — | 404 |

### 3.2 문서

| 메서드 · 경로 | 요청 | 응답 | 전이 | 오류 |
|---|---|---|---|---|
| `POST /{id}/document` | multipart `file` | `{session_id, stage, debt_count}` | S1 → S2 | 400 · 404 |

| `PATCH /{id}/extraction` | `[{debt_index, field_name, user_confirmed}]` | `ExtractionResult` | — | 404 |
| `POST /{id}/confirm` | — | `{session_id, stage}` | S2 → S3 | 404 · **409 (INV-1)** |

## 4. 데이터 모델

### 4.1 출처 추적 — `Tracked[T]`

이 서비스의 모든 값은 **값과 출처를 함께** 들고 다닌다. 화면의 출처 배지와
설명가능성 번들이 이 구조에 직접 의존한다.

| 필드 | 의미 |
|---|---|
| `value: T \| None` | **`None` 이면 UNKNOWN이며 계산에서 제외된다** |
| `source: FieldSource` | `document` · `user_input` · `user_edit` · `derived` · `unknown` |
| `confidence: Decimal \| None` | `document` 일 때만 의미 있음 (0.7 미만이면 화면 경고) |
| `page: int \| None` | 문서 근거 위치 |
| `raw_text: str \| None` | 원문 스니펫 |
| `user_confirmed: bool` | INV-1 게이트 판정에 사용 |

**금액·비율 타입 제약**

- `Money` — float 입력 거부, **원 단위 정수**만 허용
- `Ratio` — 0~1 범위 강제
- `OpenRatio` — 음수만 거부, **상한 없음**. 부담률이 100%를 넘는 상황이
  이 서비스의 핵심 대상이므로 1.0 상한을 두면 표현할 수 없다

### 4.2 채무 — `Debt`

| 필드 | 타입 | 출처 |
|---|---|---|
| `debt_id` | str | — |
| `creditor` · `product_type` · `balance` · `executed_at` · `maturity_at` · `overdue_days` · `is_secured` | `Tracked[…]` | **문서 추출** |
| `interest_rate` · `monthly_payment` · `repayment_type` | `Tracked[…]` | **보완 입력** |

> 아래 세 필드가 보완 입력인 이유는 **신용정보조회서에 없기 때문**이다(기획서 2.2 구조적 공백).
> 조회서로 "어디에 얼마"는 알 수 있지만 "매달 얼마를 갚는지"는 알 수 없다.
> 추출기가 이 값을 채워서 반환하면 그 자체가 환각이다.

### 4.3 현금흐름 결과 — `CashflowResult`

| 필드 | 타입 | 산출 |
|---|---|---|
| `total_debt` | Money | 잔액 확인된 채무 합계 |
| `monthly_total_payment` | Money | 월상환액 확인된 채무 합계 |
| `monthly_available` | Money | 소득 + 지원금 − 필수지출 |
| `monthly_shortfall` | Money | **양수 = 부족** |
| `dti_ratio` | OpenRatio ǀ None | 소득 0 또는 미입력이면 None |
| `max_overdue_days` | int ǀ None | 제도 구간 판정의 입력 |
| `secured_ratio` | Ratio ǀ None | 담보채무 비중 |
| `weighted_avg_rate` · `max_rate` | Ratio ǀ None | 금리 확인된 채무만 |
| `recent_debt_ratio` | Ratio ǀ None | **최근 6개월 신규채무 원금 비중** |
| `trace` | `CalcStep[]` | 화면의 "이 숫자는 어디서 왔나요" 펼치기 |
| `assumptions` | str[] | `"의료비 미반영"` |
| `excluded_items` | str[] | `"3건 중 1건의 월상환액 미입력"` |
| `completeness` | Ratio | 핵심 필드 확보율 |

`secured_ratio` · `recent_debt_ratio` 는 **잔액·담보여부·실행일이 하나라도 미확인이면 `None`** 이다.
부분 합계로 비율을 내면 "모른다"가 "충족"으로 둔갑하기 때문이다.

### 4.4 계산식

```
월 가용재원 = 월 실수령소득 + 정기 지원금
              − 필수생활비 − 주거비 − 의료·돌봄비 − 기타 필수 고정비
월 부족액   = 현재 월 예정 상환액 − 월 가용재원          (양수 = 부족)
부담률      = 현재 월 예정 상환액 ÷ 월 실수령소득
신규채무비율 = Σ(기준일 − 182일 이후 실행 채무 잔액) ÷ 총 채무액
```

기준일은 `as_of` 인자로 주입한다(INV-6). 오케스트레이터가 분석 시각을 넘기며,
테스트는 `now` 를 주입해 결과를 결정론적으로 재현한다.

### 4.5 경로 후보 — `PathCandidate`

기획서 7.2 결과 카드 11개 항목과 1:1 대응한다.

| # | 필드 | 화면 06 표시 |
|---|---|---|
| 1 | `path_id` · `name` | 경로명 |
| 2 | `priority` | 검토 우선순위 |
| 3 | `agency` | 담당 기관 |
| 4 | `met` | 충족된 조건 (초록) |
| 5 | `unknown` | 미확인 조건 (주황) |
| 6 | `swing_factors` | 결과를 바꿀 수 있는 요인 |
| 7 | `user_evidence` | 근거로 쓰인 사용자 답변 |
| 8 | `policy_ref` | 공식 근거 · 기준일 · 검증 여부 |
| 9 | `next_actions` | 다음 행동 |
| 10 | `consult_questions` | 상담 시 확인할 질문 |
| 11 | `why_final_check` | 왜 최종 확인이 필요한가 |

## 5. 규칙 엔진

### 5.1 3-state 조건 평가

모든 조건은 `MET` · `NOT_MET` · `UNKNOWN` 중 하나로 평가된다.

> **`UNKNOWN` 을 `NOT_MET` 으로 취급하는 것은 금지한다.**
> "조건을 충족하지 못했다"와 "확인할 수 없다"는 사용자에게 완전히 다른 의미다.
> 전자는 해당 제도가 아니라는 뜻이고, 후자는 정보를 더 모으면 달라진다는 뜻이다.

필드가 사실 목록에 없거나 값이 `None` 이면 **연산자와 무관하게 `UNKNOWN`** 이다.
`is_false` 처럼 `None` 이 그럴듯한 "아니오"로 보이는 연산자도 예외가 아니다.

**`eval()` · `exec()` 를 쓰지 않는다.** 정책 카드는 데이터이므로 코드 실행 경로가
되어서는 안 된다. 선언형 연산자만 지원하며 정의되지 않은 연산자는 예외를 던진다.

지원 연산자: `between` `lte` `gte` `lt` `gt` `eq` `in` `is_true` `is_false` `exists`

### 5.2 평가 입력 사실

| 필드 | 출처 |
|---|---|
| `max_overdue_days` · `total_debt` · `recent_debt_ratio` | `CashflowResult` |
| `secured_debt` · `unsecured_debt` | `Debt[]` 집계 (미확인 1건이라도 있으면 `None`) |
| `has_continuous_income` · `income_proof_available` | `IncomeProfile` |
| `has_secured_debt` · `has_overdue` · `income_drop_signal` | 파생 신호 |
| `court_proceeding_ongoing` · `seizure_ongoing` · `has_guarantee_debt` · `has_tax_debt` · `has_private_debt` · `legal_dispute` | `SituationFlags` |
| `monthly_available` | 트리아지용 |

### 5.3 정책 카드 6종

| ID | 제도 | 관할 | 연체 구간 | 검증 |
|---|---|---|---|---|
| `sinsok_debt_adjustment` | 신속채무조정 | 신용회복위원회 | 0–30일 | ✅ |
| `pre_debt_adjustment` | 사전채무조정 | 신용회복위원회 | 31–89일 | ✅ |
| `personal_workout` | 개인워크아웃 | 신용회복위원회 | 90일+ | ⚠️ 조건부 |
| `creditor_negotiation` | 상환조건 변경 문의 | 각 채권금융회사 | 무관 | ✅ |
| `court_rehabilitation` | 개인회생·파산 상담 | 법원 | 무관 | ✅ |
| `complex_support` | 복합지원 상담 | 서민금융통합지원센터 등 | 무관 | ✅ |

**신복위 제도 공통 조건** — 총 채무액 15억 원 이하(무담보 5억 · 담보 10억),
최근 6개월 신규채무 원금이 총 채무원금의 30% 미만, 계속적·반복적 소득 존재.

**신속채무조정 특례** — 연체가 없어도 최근 6개월 내 실업·무급휴직·폐업,
90일 이상 입원, 개인신용평점 하위 10%(또는 하위 20% & 연소득 4,500만원 이하) 등에
해당하면 신청 가능하다. 자가신고 항목이라 자동 판정하지 않고 상담 안내로 처리한다.

**개인워크아웃 총채무액 한도는 확정하지 않았다.** 신용회복위원회 웹사이트 두 페이지가
서로 다른 값(제도 상세 15억 / 제도 비교 25억)을 제시한다. 어느 쪽이 최신인지 확인되지
않아 조건으로 인코딩하지 않고 카드의 `unresolved` 블록에 양쪽 값과 출처를 보존했다.
**유리한 쪽으로 추정하지 않는다.**

### 5.4 경로 선별과 정렬

```
사실 조립 → 카드별 3-state 평가 → 필수 조건 NOT_MET 이면 EXCLUDED
         → priority 순 정렬 → 상위 3개 반환
```

**정렬 기준은 `priority` 가 먼저, `status` 는 동순위 안에서만 쓴다.**

status 를 먼저 정렬하면 조건이 1개뿐인 보조 경로(금융회사 협의·법원 상담·복합지원)가
항상 `CANDIDATE` 로 떠서, 조건이 많아 `NEEDS_INFO` 가 되기 쉬운 신복위 핵심 제도를
상위 3개 밖으로 밀어낸다. 실제로 연체 34일 이용자에게 사전채무조정이 아예 노출되지
않는 결함이 있었다(`docs/평가결과.md` 참조).

### 5.5 판정 불가

| 조건 | 처리 |
|---|---|
| `max_overdue_days` 미확인 | `undetermined=True` |
| `total_debt` 미확인 | `undetermined=True` |
| 미해소 상충 정보 존재 | `undetermined=True` |
| 사용 가능한 정책 카드 0개 | `undetermined=True` |

**판정 불가 상태에서도 현금흐름 결과는 제공한다.** 제도를 판정할 수 없어도
자신의 상환 부담을 아는 것은 독립적인 가치가 있다(기획서 7.3).

### 5.6 트리아지

전문기관 상담을 우선 안내해야 하는 상황을 먼저 걸러낸다. `REFER` 판정이면
규칙 엔진을 생략하되 **현금흐름 섹션은 그대로 남긴다.**

## 6. 화면 명세

모바일 우선(`max-w-md`), 서버 사이드 렌더링. 공통 레이아웃에 7단계 진행 표시,
"글씨 크게" 토글(`localStorage` 저장), 정책 기준일 표기가 있다.
**미검증 정책 카드가 포함되면 최상단에 빨간 개발 모드 배너**가 뜬다.

### 공통 표현 규칙

| 요소 | 규칙 |
|---|---|
| 확정 숫자 | 초록 **실선** 박스 + "✓ 확정 숫자" 배지 |
| 검토 후보 | 주황 **점선** 박스 + "? 검토 후보 (확정 아님)" 배지 |
| 출처 배지 | 문서(파랑) · 입력(회색) · 수정(보라) · 미확인(빨강) |
| 낮은 신뢰도 | "⚠ 확인 필요(신뢰도 낮음)" (`role="alert"`) |

확정과 후보를 **선의 종류로도 구분**한다. 색만으로 구분하면 색각 이상 이용자가 읽을 수 없다.

### 화면별

| # | 파일 | 제목 | 다음 단계 조건 |
|---|---|---|---|
| 0 | `00_landing.html` | 시작 | `/start` → 세션 생성 후 리다이렉트 |
| 1 | `01_intro.html` | 소개·동의 | 개인정보 동의 체크 필수 → `POST /consent` |
| 2 | `02_upload.html` | 업로드 | PDF 또는 이미지 선택 → `POST /document` |
| 3 | `03_extraction.html` | 추출 확인 | 전 채무 확인 → `PATCH /extraction` → `POST /confirm` |
| 4 | `04_supplement.html` | 보완 입력 | `POST /supplement` → 연속 `POST /analyze` |
| 5 | `05_result.html` | 현금흐름 결과 | 링크 이동 (API 호출 없음) |
| 6 | `06_paths.html` | 경로 비교 | `POST /plan` |
| 7 | `07_plan.html` | 계획·요약서 | `POST /report` → PDF 다운로드 (마지막) |

**01 소개·동의** — 유의사항 4항목을 명시한다: ① 금융·법률 자문이나 신용평가가 아님
② 제도 검토 결과는 자격 확정이 아님 ③ 현금흐름 계산 결과만 확정 숫자
④ 업로드 원본은 세션 종료 또는 TTL 만료 시 자동 삭제.
신용정보조회서가 없는 이용자를 위해 크레딧포유 무료 발급 경로를 안내한다.

**03 추출 확인 (INV-1 게이트)** — 채무별 카드에 채권자·유형·잔액·연체일수와
각 값의 출처 배지를 표시한다. 신뢰도 0.7 미만이면 경고를 띄운다.
확인 체크박스를 `PATCH /extraction` 으로 전송한 뒤에야 `POST /confirm` 을 호출한다.
**미확인 항목이 남아 있으면 전송 전에 사용자에게 알린다.**

**04 보완 입력** — 채무별 금리·월상환액 일괄 입력 + 고정 질문 + 조건부 질문.
"모르면 건너뛰어도 됩니다"를 명시하고, 건너뛸 때 계산에 미치는 영향(`skip_impact`)을 함께 보여준다.

**05 결과** — 최상단에 월 부족액(또는 여유자금)을 확정 숫자 박스로 크게 표시한다.
총 채무액·월 가용재원·월 예정 상환액·부담률을 2열로 배치하고,
채권자별 채무 비중과 가용재원 대비 상환액을 막대로 보여준다.
`<details>` "이 숫자는 어디서 왔나요"를 펼치면 계산 과정(`CalcStep`)이 나온다.

**06 경로 비교** — 최대 3개. 각 경로에 11개 항목을 번호와 함께 표시한다.
정책 근거는 `제목 (카드 버전) · 기준일` 형식이며, 미검증 카드는 빨간 글씨로
"공식 출처 대조 전(미검증)"을 덧붙인다. 제외된 경로는 접힌 영역에서 사유와 함께 볼 수 있다.

**07 계획·요약서** — 7일 실행계획을 시점 배지(오늘 / 1일 이내 / 2일 이내 / 상담 전 / 상담 후)와
함께 나열한다. 요약서 PDF는 **포함할 항목을 이용자가 선택**한다
(채권자명 · 소득 · 검토 경로 · 상담 질문).

## 7. 안전성 설계

금융보안원 「금융 AI 안전성·신뢰성 평가 프레임워크」(2026-08) 10개 항목 대응이다.

### 7.1 신뢰성

| 항목 | 구현 |
|---|---|
| 모델 성능 관리 | `eval/E1~E2` 추출 F1·숫자 정확도, 신뢰도 0.7 미만 화면 경고 |
| 데이터 품질 | 합성 조회서 + 경계값·예외 사례, 정책 카드 출처·기준일·검증 상태 관리 |
| 공정성·편향성 | 낙인 표현(`무책임` `방만` `빚더미` `신용불량자`) 전 섹션 차단 |
| 설명가능성 | `Tracked` 출처 추적, `CalcStep` 계산 과정, `GET /explain` 번들 |

### 7.2 안전성

| 항목 | 구현 |
|---|---|
| AI 특화 보안위협 | 문서 인젝션 스캔 — 매치된 **라인만 제거**하고 문서 전체를 거부하지 않는다 |
| 공격 탐지·대응 | 인젝션 패턴 8종, 세션 위반 횟수 누적 |
| 자산 보호 | PII 마스킹, 파일명 재생성(경로 조작 차단), **TTL 자동 삭제** |
| 외부 모델 검증 | 추출 스키마 검증 + 재시도, 숫자 그라운딩 대조 |
| 기존 보안 확장 | 업로드 크기·MIME·확장자 3중 검증 |
| 검증·운영관리 | 감사 로그 편집(`redact`), 레드팀 배터리 |

### 7.3 출력 필터

| 카테고리 | 적용 섹션 | 예 |
|---|---|---|
| `confirmatory` | **경로·계획만** | `신청 가능합니다` · `가장 유리` · `반드시 승인` |
| `stigmatizing` | 전체 | `무책임` · `빚더미` · `신용불량자` |
| `risky_advice` | 전체 | 의도적 연체 · 재산 은닉 · 허위 신고 · 임의 상환 중단 |
| `privacy_request` | 전체 | 다른 이용자 정보 요구 |

> `confirmatory` 를 경로 섹션에만 적용하는 이유: **현금흐름 섹션의 확정 표현은 허용되어야 한다.**
> "매달 13만 원이 부족합니다"는 확정 계산 결과이므로 단정해도 된다.
> 제도 적합성에 대해서만 단정을 막는다. 이것이 "숫자는 확정, 제도는 후보" 원칙의 구현이다.

필터에 걸린 문장은 폐기하고 **결정론적 템플릿 문장으로 대체**한다.
검증되지 않은 LLM 출력이 화면에 도달하는 경로는 없다.

### 7.4 PII 마스킹

적용 순서가 중요하다: 주민등록번호 → 카드번호 → 전화번호 → 계좌번호 → 이메일 → 주소.
치환 형식은 `[MASKED:<종류>]` 이다.

**금융회사명·금액·날짜는 마스킹하지 않는다.** 과잉 마스킹은 추출 성능을 떨어뜨린다.
계좌번호 패턴이 날짜를 오탐하지 않도록 패턴을 설계했다.

### 7.5 TTL 자동 삭제

세션이 만료되면 `upload_dir/{session_id}/` 를 통째로 삭제하고 세션 레코드도 지운다.
스위퍼는 앱 lifespan 에 배선되어 주기적으로 실행된다.
화면과 요약서가 약속하는 "세션 종료 시 자동 삭제"가 실제로 지켜지도록 하는 장치다.
