### E3 제도 후보 누락률 — 0.10 → 0.00

측정 과정에서 **실제 결함 하나를 발견해 수정**했다.

`case_091`~`case_100`(연체 34일 등, 사전채무조정 대상) 10건에서 기대 제도가
결과 목록에 **아예 나타나지 않았다.** 원인은 `rules/engine.py` 의 정렬 기준이었다.

```python
# 수정 전 — status 가 priority 보다 앞
candidates.sort(key=lambda p: (_STATUS_RANK[p.status], p.priority, len(p.unknown)))
```

조건이 1개뿐인 보조 경로(금융회사 협의·법원 상담·복합지원)는 항상 `CANDIDATE` 가 되고,
조건이 많은 신복위 핵심 제도는 미확인 조건 하나만 있어도 `NEEDS_INFO` 가 된다.
status 를 먼저 정렬하면 보조 경로 3개가 `max_paths=3` 을 모두 채워
**연체구간이 맞는 핵심 제도가 화면에서 사라진다.**

연체 34일 이용자가 "법원 개인회생 상담"과 "복합지원"만 보고
정작 대상인 **사전채무조정을 안내받지 못하는** 상황이었다.

`NEEDS_INFO` 는 "해당 없음"이 아니라 "무엇을 확인하면 되는지 알려주는 상태"이므로,
priority 를 먼저 정렬하고 status 는 동순위 안에서만 쓰도록 바꿨다.

### 입력 완성도 0.6422 — 목표 미달 (설계상 예상된 값)

핵심 필드 확보율이 64%에 그치는 이유는 **신용정보조회서에 금리와 월 상환액이 없기 때문**이다
(기획서 2.2 구조적 공백). 이 두 필드는 추출 대상이 아니라 보완 입력 대상이므로,
문서만으로 측정하면 구조적으로 90%에 도달할 수 없다.

**측정 정의를 바꾸는 것이 옳다** — 보완 입력 단계(S4)를 거친 뒤의 완성도를 재는 것이
서비스 실제 흐름과 맞는다. 현재 값은 "업로드 직후" 시점의 값이다.

### E1 — 로컬 오픈모델 실측 0.9975, 과정에서 버그 2건 발견·수정

`ANTHROPIC_API_KEY` 없이 Qwen2.5-7B-Instruct(GGUF Q4_K_M, `llama-cpp-python`)로
실행했다. 첫 시도는 55건 중 1건째에서 곧바로 스키마 검증 실패로 죽었다 —
원인은 이 프로젝트 코드 쪽 결함 2건이었고, 로컬 모델이 우연히 드러낸 것이다.

1. **JSON을 ` ```json ` 코드펜스로 감싸 응답** — `LocalClient.complete()`에
   `response_format={"type": "json_object"}`(그래머 제약 디코딩)를 추가해 해결.
2. **필드 이름을 문서의 한국어 표기로 번역해서 응답**("채무 목록", "금융회사명" 등) —
   기존 `build_user_prompt()`가 키 이름을 한 번도 예시로 보여주지 않았다는,
   Anthropic 경로에도 그대로 있던 잠재 결함. 영문 키 이름을 명시적으로
   예시와 함께 프롬프트에 넣어 해결(`src/dn/extraction/prompts.py`).

수정 후 재실행하니 55건 전체가 스키마를 만족했고, 필드별 F1도 대부분 1.0000이었다
(연체일수 0.9875, 담보여부 0.9975만 소폭 미달 — 상세는 위 필드별 표 참고).

**CPU 스레드 튜닝도 실측으로 확인했다.** 이 서버(Xeon w7-3465X, 56 논리 코어)에서
기본값(전체 논리 코어)으로 돌리면 0.29 tok/s, 물리 코어 근사치(28)로 제한하면
18.5 tok/s — 64배 차이였다. `LocalClient`는 스레드 수를 명시하지 않으면 자동으로
논리 코어의 절반(최대 16)으로 제한한다.

### E2 — 로컬 오픈모델 실측 0.9901

E1과 같은 실행(같은 클라이언트, 같은 프롬프트 수정 적용 후)에서 잔액·연체일수
두 필드를 다시 채점했다. 잔액은 202/202(1.0000), 연체일수는 197/201(0.9801) —
E1의 `overdue_days` 오류 4건(1건 오추출 + 3건 미추출)과 일치한다. 전체
정확도 0.9901(399/403)로 목표(0.95)를 넘었다.
